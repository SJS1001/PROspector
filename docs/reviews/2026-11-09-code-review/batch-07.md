# Batch 7: site: per-intent idempotency keys and CSRF-refresh retry in the discovery, contacts and prospecting clients; future-only defer dates

Severity: medium. App: site. Base branch: `claude/owner-local-completion-20261109`.

Files: `site/app/discovery/discovery-workspace.tsx`, `site/app/prospects/contacts-workspace.tsx`, `site/app/prospecting/prospecting-workspace.tsx`, `site/app/prospecting/review-queue.tsx`, `site/app/prospecting/review-command.ts`

Findings: Market Discovery caches idempotency keys forever per logical name, so a repeat run replays the old result and a key shared across products errors; Contacts grant confirmation reuses one idempotency key per mount, so a second grant for a different prospect is impossible without a page reload; Single-use CSRF token is consumed before command validation, and no POST error re-issues one, so the next prospecting command fails as 'outcome unknown'; Review Defer sends past dates and the server's validation error is shown as 'changed in another tab'

FINDING 1 (medium). discovery-workspace.tsx:16 operationKey(logical) caches a UUID per logical name ('discover', 'ready', 'synthetic', `proposal:${id}`) in a useRef Map and never deletes it. mutate (:44) keeps it after success. The server digests (workspace, productId, expectedProductRevision, triggerKind, idempotencyKey) (market-discovery.ts:154-168; decideMarketPlayProposal :882) and replays on a match or returns 409 on a mismatch (discovery-handler.ts:90). Failures: (a) Discover again on the same product and revision silently replays the first run. (b) Switch product and Discover: 409, which mutate maps to state 'unknown' and the projection is discarded. (c) A second decision on a proposal conflicts. Fix: scope the logical key to the full intent (include productId, expectedProductRevision and, for proposals, the decision), keep the key only across an unknown-outcome retry of that same intent, and delete it on success or on a definitive failure. Handle 409 explicitly: refresh the projection rather than mapping it to 'unknown'. Use existing copy strings only.

FINDING 2 (low, latent because the production route passes no commandService). contacts-workspace.tsx:63 `const [grantKey] = useState(() => crypto.randomUUID())` is sent on every create_grant_confirmation (:79) and is never rotated (loadProjection at :75 clears identityKeys and runAttempt only). The server returns idempotency_conflict when prospectIds or sourceRevision differ (enrichment-grant-issuance.ts:63-75), which becomes 409 and the 'authority changed' copy. Fix: mint the key per (prospectId, expectedProspectRevision) intent, keep it only for an unknown-outcome retry of that intent, and drop it on success or a definitive failure.

FINDING 3 (low). Server POST handlers consume the single-use CSRF token before validation (prospecting-handler.ts:15, and likewise discovery and contacts). Every post-consumption error (409/400/404/413) returns without a new cookie, so the next POST gets 403 invalid_csrf_token. prospecting-workspace.tsx:126-154 does not recover from 403; it falls into `!response.ok -> throw -> setNotice('unknown')` ('The outcome could not be verified'), although the server refused deterministically. Fix (client side only): in prospecting-workspace.tsx, discovery-workspace.tsx and contacts-workspace.tsx, on a 403 whose body error is 'invalid_csrf_token', re-GET the projection (which issues a fresh token) and retry the same command ONCE with the SAME idempotency key, matching knowledge-workspace.tsx:77-83. A second 403 shows the existing failure notice. Never retry on any other status.

FINDING 4 (low). The defer reviewAt input in review-queue.tsx:186-196 has no min, and review-command.ts:32-34 only checks Number.isFinite. The server throws ProspectReviewError for reviewAt<=now (prospect-review.ts:78), and that maps to 409. prospecting-workspace.tsx:141-144 maps every 409 to 'This candidate changed in another tab...'. Fix: set a `min` on the datetime-local input (now, rounded up to the next minute, in local time), and make buildReviewCommand return a validation error for reviewAt <= now. The form shows an inline validation message and does not POST. DO NOT change the 409 'stale' copy: it is pinned by site/tests/profile-prospecting-ui.test.mjs:564 and site/tests/browser/operator-journey-e1.spec.ts:12. Distinct server error codes are an open owner question, not this PR.
