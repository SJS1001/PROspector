# Batch 8: site: Contacts read projection honours configured freshness windows and re-checks suppression and drift

Severity: low. App: site. Base branch: `claude/owner-local-completion-20261109`.

Findings: Contacts readiness and the eligibility snapshot ignore the profile's configured contact freshness windows; Contacts read projection never re-checks suppression or knowledge drift after a snapshot is persisted

## Brief

Repo: PROspector. Work only in site/. Base branch: claude/owner-local-completion-20261109. Before editing, read AGENTS.md and the root COMPLETION_LEDGER.md.

Both findings are latent in production: the only live writer of contact_eligibility_snapshots is the DEV-only C4 lane, and persistCurrentContactEligibilitySnapshot has no caller. They do show up in the C4 lane today. This PR makes the Contacts read projection fail closed before a production writer exists.

FINDING 1 (low). contacts-handler.ts:279 fresh() computes maxAge only from DEFAULT_CONTACT_FRESHNESS_MS (30 days mailbox-verified email, 90 days source-verified email or phone). persistAfterActivation (contact-eligibility-persistence.ts:139-162, strategy at :156-159) passes no *FreshnessMs fields, so normalizeStrategy (contact-eligibility.ts:195-203) uses the defaults. Person discovery uses the configured contact_strategy windows: deriveContactFreshnessPolicy (person-discovery-repository.ts:132), staleTrustedObservations (person-discovery-handler.ts:229-240) and the stale_refresh trigger (drizzle/0019_person_discovery.sql:312-350). The C4 seed sets a 7-day mailbox window (person-discovery-c4-acceptance.ts:94), so on day 8 person discovery calls an observation stale while /api/contacts still says ContactReady and 'current' until day 30. With a 60-day window it is the reverse: Contacts says stale at day 31, but stale_refresh is refused until day 60.
Required fix: export or reuse deriveContactFreshnessPolicy from person-discovery-repository.ts. In persistAfterActivation, derive the policy from the snapshot's configuration manifest and pass all three windows into the projectContactEligibility strategy. In the Contacts read (SNAPSHOT_SELECT at contacts-handler.ts:144 already joins typed_configurations), derive the same policy from manifest_json and use it in fresh(), exactFreshReservationIds, recheckSnapshot and toPublicContactObservation. If the policy cannot be derived, treat evidence as NOT fresh (fail closed). Do not edit contact-eligibility.ts or migrations.

FINDING 2 (low). recheckSnapshot (contacts-handler.ts:248) re-validates lineage, freshness and attestation only. Suppression and open knowledge drift are evaluated only at write time (contact-eligibility-persistence.ts:136-137, matchingSuppressionRefs/hasCurrentDrift). Neither an outreach_suppression_tombstones insert nor a knowledge_drifts row changes a prospect or configuration revision, and no trigger invalidates snapshots (0010_governed_outreach.sql:660-740 has only scope and immutability guards). So a suppressed or drift-blocked contact stays ContactReady/eligible on /api/contacts. The send path re-checks both (outbox.ts:352-360), so this is a read-projection defect, not a send bypass.
Required fix: in loadContactsPage/recheckSnapshot, re-check open knowledge_drifts for the snapshot's configuration and suppression or tombstone subjects for the contact, using the same predicates as matchingSuppressionRefs and outbox.ts:352-360. Import or share the predicate; do not copy the SQL loosely. On a match, downgrade ContactReady to NonContactable (suppressed) or NeedsReview (drift), with reason codes contact_suppressed / contact_drifted, and eligible=false. Do not edit outbox.ts.
