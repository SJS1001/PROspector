### 1. [medium, confirmed] Material-signal re-entry accepts repeated or pre-decision evidence, bypassing the 90-day rejection cooldown

- Area: site-prospecting-review; location: `site/domain/prospect-review.ts:56`
- Problem: materialSignal (line 52) is any signal with material=1 in the current submission. reentryKind (lines 56-60) then gives 'material_signal' to a rejected prospect, or to a deferred prospect before its review date, with no check that the signal is new. Nothing checks that it was observed or retrieved after the owner's decision, or that it differs from the evidence cited in the rejected assessment. The sourced-disproof path does require post-decision timestamps, and the test asserts that pre-decision evidence cannot be used there. CONTEXT.md defines a Material Signal as 'A new Signal'. It also says 'Republication or repetition of known information is not material'. Signals are stored per submission with no cross-submission dedupe (source-policy.ts line 44 only checks NOT EXISTS for the same submission_id), so a re-observed event becomes a fresh material row.
- Failure scenario: The owner rejects prospect P (cooldown ends at now+90d) after reviewing an assessment that cites material event E (kind 'operating-signal', observedAt within 24h before the run watermark W). The next run's window is designed to overlap: lowerExclusive = W - DAY (prospecting-schedule.ts:74). The runner re-reports E, the materializer proposes the same target, and persistQualificationAssessment sees state='rejected' plus a material signal. It records a 'material_signal' prospect_reentry_event and inserts a new active 'qualified' prospect. The owner's Reject is undone on the next run using the same evidence they rejected. The same applies to Defer before reviewAt. This is latent in production while the materializer is reject-only.
- Suggested fix: Count a signal as a re-entry Material Signal only if it was retrieved and observed after priorInactive.decision_at. Its observation fingerprint (or kind plus underlying origin plus occurredAt) must also not appear in the prior assessment's evidence_json or in any earlier submission for this profile. Add a regression test that re-submits the same material event after rejection and expects 'cooldown remains active'.
- Verifier: The core defect is real. At prospect-review.ts:52 and :56-59, any signal from the candidate's own submission with material=1 qualifies as a Material Signal. `material` is a pure kind check (source-policy.ts:14). Nothing compares the signal against decision_at or against the rejected assessment's evidence. The sourced-disproof path does both (source-policy.ts appendSourcedDisproofValidationMarker requires occurred_at and retrieved_at > decision_at). The reviewer's specific scenario is wrong, though. Under the same configuration, materializeCandidate (prospecting-ingestion.ts:268-269) reuses the existing candidate with the same configuration_id and fingerprint. That candidate's original run and submission signals are re-read, so the assessment digest matches the existing assessment, and line 51 returns early with no re-entry. The overlapping next scheduled run therefore cannot reopen the rejection. The reachable route is a Profile configuration replacement. Activation creates a new initial run with window_lower_exclusive NULL (profile-readiness.ts:179), so the runner may re-report the exact pre-decision event E. That run produces a new candidate (a new configuration_id), and a 'material_signal' reentry event plus a new active qualified prospect are written during the 90-day cooldown. The repo's own test follows this path (configuration replacement, then material re-entry) but uses a post-decision observedAt. Downgraded to medium because production uses the reject-only materializer (ingestion.ts:26,78; runner-runtime passes no materializer), so the defect is latent. Not D1-test-verified.
