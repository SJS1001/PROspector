# Batch 5: site: prospecting run liveness (manual watermark wedge, retry after capability expiry, overlap guard, intent replay)

Severity: medium. App: site. Base branch: `claude/owner-local-completion-20261109`.

Files: `site/domain/prospecting-schedule.ts`, `site/domain/prospecting-handler.ts`, `site/domain/runner-assignment.ts`, `site/domain/prospecting-run-admission.ts`, `site/tests/prospecting-schedule-misfire.test.mjs`, `site/tests/prospecting-ingestion-lifecycle.test.mjs`

Findings: A manual run can permanently wedge schedule reconciliation (watermark >= due slot throws every pass); Retryable ingestion failures and abandoned claims become unrecoverable once the runner capability expires; The overlap guard ignores blocked runs, and admission does not re-check overlap, so concurrent runs per profile can both be queued; createProspectingIntent has no conflict recovery: a concurrent duplicate gets a raw constraint error (500) instead of a replay

## Brief

Repo: PROspector. Work only in site/. Base branch: claude/owner-local-completion-20261109. Before editing, read AGENTS.md and the root COMPLETION_LEDGER.md.

GOAL: one PR that removes four latent liveness and concurrency defects in prospecting scheduling and runner ingestion. None is wired to a cron or a production route yet, so fix them before wiring.

FINDING 1 (medium, liveness). manual_find (prospecting-handler.ts:25) attaches the active scheduleId to manual runs. completeProspectingRun (prospecting-schedule.ts:177) unconditionally sets schedules.last_successful_watermark to the run's window_upper_inclusive, which for a manual run is its creation time. If that is at or after an unreconciled next_run_at, profileSourceWindow(watermark, due) throws in createProspectingIntent (:102/:106) and in persistSkippedMisfire (:206). Both run before advanceSchedule (:136/:148, :151/:152), so next_run_at never moves, every reconcile throws 'Invalid prospecting window watermark', and the throw escapes the loop and starves every later schedule (ordered by next_run_at). The comment at :63-66 names this case. A scratch probe: due=2026-11-09T11:00Z with watermark=due+5m; reconcile at due+30m and at due+2d both threw with 0 writes.
Required fix: (a) manual runs must not move the schedule watermark past an unreconciled due slot. Either stop attaching schedule_id to manual runs, or in completeProspectingRun set watermark = MAX(current, run upper) capped below the schedule's next_run_at. Pick the option that keeps the existing manual-run tests' intent and explain why. Also never regress the watermark (MAX), which fixes the Finding 3 side effect. (b) In reconcileProspectingSchedules, when the window is inverted for a schedule, record a skipped row with a distinct reason (reuse an existing skip vocabulary if one fits; otherwise add one in code, with no migration) and still call advanceSchedule. (c) Isolate errors per schedule: catch per iteration, record or log, and continue, so one schedule cannot abort the loop. Do not swallow errors silently. Return per-schedule failures to the caller.
Tests first (site/tests/prospecting-schedule-misfire.test.mjs): reproduce the probe (due=T, a manual run completes at T+5m, then reconcile at T+30m and at T+2d). Expect no throw, the slot recorded as skipped with the reason, next_run_at advanced, and later schedules still processed. A second schedule ordered after a failing one still gets its intent.

FINDING 2 (medium, non-idempotent retry). submitRunnerObservations (runner-assignment.ts) rejects on capability.expiresAt<=now (:58) and assignment.expires_at<=now (:60) BEFORE the exact idempotent-replay check (:64). handleRunnerIngress is the only production route into processAcceptedRunnerSubmission. A 'processing_retryable' ingestion failure sets the run to 'submitted' (prospecting-ingestion.ts:102,213). A worker crash leaves it 'validating'. After the TTL (at most 5 minutes) a same-key re-POST is refused (404), and issueRunnerAssignment will not issue a new assignment (has_submission=1; acceptedPartialRetry only matches 'partial_submission_retryable', :16-19). No sweeper exists, so the run stays stuck forever. Both states are in the scheduled-overlap active list (prospecting-schedule.ts:98), so every later slot for that profile becomes skipped_overlap indefinitely. Also, the handler (prospecting-handler.ts:18) returns 200 {submissionId, replayed} even when processing is 'pending' (lease held by another worker) or retryable, so the runner gets no retry signal.
Required fix: in submitRunnerObservations, after verifying the capability signature/MAC and scope but BEFORE the expiry checks, accept an EXACT idempotent replay: same assignment id, same idempotency key, same operation digest as an already-received submission. Route it to reprocessing only. A non-matching or new submission after expiry must still be rejected exactly as today (fail-closed; never accept new data on an expired capability). In handleRunnerIngress, return a non-2xx retryable status (for example 503 with a retry_after hint, or 409 'processing_pending'; choose one and document it) when processing is pending or retryable, and 200 only when processing reached a terminal accepted state.
Tests first (site/tests/prospecting-ingestion-lifecycle.test.mjs): issue a capability with a short TTL, submit, force a processing_retryable failure, advance the clock past expiry, re-POST with the same key and digest, and expect reprocessing to complete. Re-POST with a different digest after expiry is still rejected. A brand-new submission after expiry is rejected. A pending claim returns non-2xx.

FINDING 3 (low, race; latent because the production admission port is reject-only). The overlap guard (prospecting-schedule.ts:97-100) counts only queued/assigned/running/submitted/validating. Every intent is created as 'blocked_missing_capability' (:102/:111). admitProspectingRunToQueue (prospecting-run-admission.ts:115, 153-178) checks only run revision, state and active configuration. Two scheduled intents for one profile can both be admitted and run in parallel, and with the old unconditional watermark write the later completion can regress the watermark.
Required fix: add NOT EXISTS (another run for the same workspace and profile in queued, assigned, running, submitted or validating) to the admission command's guarded write predicate, and refuse with the existing conflict error. Optionally also count blocked_missing_capability scheduled intents in the overlap guard. If you do, manual intents keep skipping the guard by design. No migration.
Test first: create two blocked intents for one profile, admit the first and then the second, and expect the second refused.

FINDING 4 (low, non-idempotent retry). createProspectingIntent does check-then-insert (prospecting-schedule.ts:79-85), and its database.batch (:109-113) has no catch, unlike persistSkippedOverlap/persistSkippedMisfire (:191, :213-216). A concurrent duplicate hits prospecting_run_idempotency_unique (drizzle/0007:227) or authority_command_key_unique (0004:42), and the raw D1 error becomes 500 server_error in prospecting-handler conflict()/denial(). In reconcile it aborts the loop.
Required fix: wrap the batch with a catch that re-reads by (workspace_id, idempotency_key) and returns {replayed:true} when trigger_kind and trigger_key match. Otherwise throw ProspectingScheduleConflictError (mapped to 409).
Test first: simulate the race by inserting the winner row between the prior check and the batch (or calling twice with a stubbed prior read), and expect a replay, not a throw.
